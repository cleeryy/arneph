## 1. Verdict

Le socle est sain : TypeScript strict, Zod aux frontières, 435 tests, service role
confinée par `server-only`, mapping snake_case centralisé, positions 1-based
cohérentes, preview éditeur qui réutilise les composants du lecteur. Ce n'est pas
un code « à jeter ».

Les risques réels sont concentrés sur trois axes :

1. **Autorisation** : aucune identité, aucune validation des chemins Storage, des
   actions destructives accessibles publiquement avec la clé service role.
2. **Intégrité des données** : sauvegarde non transactionnelle et, surtout, les
   sections supprimées ne sont **jamais** supprimées en base.
3. **Pipeline image** : les images longues (cœur du produit) ne sont pas bornées
   correctement, aucun downscale n'est appliqué, les sprite sheets sont décodées
   en parallèle avant le garde-fou mémoire.

S'y ajoutent deux bugs de navigation très visibles (inertie de molette, Firefox)
et une dette de découpage sur les gros composants.

**Comptage : 3 P0 (dont 1 conditionnel), 16 P1, ~30 P2, ~35 P3.**

## 2. P0 — à traiter avant toute exposition publique

### P0-1 — DATA — Les sections supprimées ne sont jamais supprimées en base

`src/app/editor/actions.ts:317-320` calcule `removedIds`, mais `:362-364` ne
l'utilise que pour nettoyer le Storage. `deleteSection` n'est appelé qu'au
rollback (`:195`). Aucun autre chemin de suppression n'existe (vérifié par grep).

**Séquence réelle** :
1. L'utilisateur supprime une section dans l'éditeur, sauvegarde → `{ ok: true }`.
2. Les fichiers Storage de la section sont supprimés (`cleanupSectionStorage`).
3. La ligne `sections` reste en base.
4. Au rechargement, la section réapparaît, avec des images cassées.
5. `publishWebtoon` (`actions.ts:462`) compte ces fantômes comme des sections.
6. `sections: []` efface tous les assets sans vider la base.

**Correctif** : supprimer les sections retirées **après** le reorder réussi, en
un seul batch :

```ts
await reorderSections(wid, orderedIds);
if (removedIds.length > 0) {
  await deleteSectionsBatch(wid, removedIds); // delete().in("id", removedIds).eq("webtoon_id", wid)
}
await removeStoragePaths(...);
```

Idéalement, plier cette suppression dans la RPC transactionnelle (P1-2). Un
`deleteSection` unitaire au milieu du save actuel fabriquerait des états
partiels supplémentaires.

**Test manquant** : aucun test n'assert que les sections retirées sont supprimées
(`actions.test.ts` ne vérifie que le rollback). C'est l'angle mort n°1.

### P0-2 — SEC — Frontière d'autorisation absente (actions + chemins Storage)

**2a. Identité.** Les 7 Server Actions (`createWebtoonAction`,
`updateWebtoonMetadataAction`, `saveWebtoon`, `publishWebtoon`,
`unpublishWebtoon`, `deleteWebtoonAction`, `actions.ts:209-559`) sont des
endpoints POST publics, sans `getUser`/`getSession`/`middleware` (vérifié). Elles
tournent avec `SUPABASE_SERVICE_ROLE_KEY` (`src/lib/db/server.ts:129-149`), qui
contourne RLS. `deleteWebtoonAction` accepte n'importe quel UUID.

À noter : la RLS activée **sans policy** (`20260801174351_init.sql:76-87`) n'est
pas la vulnérabilité — c'est au contraire la seule barrière restante sur les
tables. Le trou est l'absence d'authentification devant les actions.

**2b. Chemins Storage.** Les configs client (`imagePath`, `spritePath`, `fxPath`,
`storagePath`) sont validées comme de simples `z.string().min(1)`
(`schemas.ts:26,38,50,60`) puis persistées telles quelles. `saveWebtoon` supprime
ensuite, avec la service role, tout chemin précédemment persisté qui n'est plus
dans le payload (`actions.ts:354-360`). Un appelant peut donc enregistrer un
chemin vers l'objet d'un autre webtoon, puis le faire supprimer au save suivant.
Le même problème existe au rendu : `StepImage` construit une URL imgproxy depuis
un chemin non validé.

**Correctif** :
- Décider le mécanisme d'identité : Supabase Auth + `owner_id` (multi-utilisateur)
  ou SSO edge (Cloudflare Access / Authentik) **vérifié côté serveur** (JWT, pas
  un simple header). `requireEditor()` en tête de chaque action et garde dans les
  pages `/editor`.
- Valider chaque chemin contre le préfixe attendu :
  `webtoons/sections/<sectionId>/`, `webtoons/covers/`, `webtoons/seed/`.
  Rejeter `..`, les chemins absolus et les préfixes croisés.
- Ne jamais supprimer un chemin hors de ces préfixes, même avec la service role.
- Ne pas exposer l'app en direct sur `0.0.0.0:3000` si l'edge est la seule
  protection : firewall/LAN ou bind localhost.

**Décision requise** : tant que le mécanisme d'identité n'est pas choisi,
l'estimation « auth en 1-3 j » est fausse. Un palliatif à 1 h (basic auth ou
Cloudflare Access) ferme l'accès mais ne remplace pas une vraie autorisation.

### P0-3 — SEC — Policies Storage `anon` totales (conditionnel : vérifier la prod)

`supabase/migrations/20260802_e2e_storage_policies.sql:4-18` crée
`INSERT`/`UPDATE`/`DELETE`/`SELECT` sans clause `TO` → politiques appliquées à
`PUBLIC`, donc à `anon`. La clé anon est publique par nature
(`src/lib/supabase/upload.ts:19-28`).

**Impact si la migration est appliquée en prod** : n'importe quel visiteur peut
supprimer ou écraser toutes les images du bucket, et uploader du HTML/SVG servi
depuis l'origine Supabase (XSS stocké, hébergement d'abus).

**À faire d'abord** : vérifier `supabase_migrations.schema_migrations` en prod
pour savoir si cette migration « e2e » a réellement été appliquée. Si oui :
1. Supprimer `UPDATE` et `DELETE` anon ; garder `INSERT`/`SELECT` seulement si
   l'upload navigateur sans auth est assumé.
2. Restreindre MIME et taille au niveau du bucket.
3. Faire tourner la clé anon après correction (elle est dans le bundle).
4. Vérifier ensuite qu'un `DELETE` anon renvoie bien 403.

Si la migration n'est pas appliquée, la sévérité tombe à P1 « risque de
déploiement » — mais le fichier ne doit pas rester dans le jeu de migrations prod.

## 3. P1 — pertes de données, bugs majeurs, perf critique

### DATA-2 — Sauvegarde non transactionnelle, sans verrou optimiste

`saveWebtoon` (`actions.ts:307-369`) enchaîne `getWebtoon` → N × `upsertSection`
→ N × `createSection` + `syncImages` → `reorderSections` (N updates) →
nettoyages. Chaque étape est un aller-retour PostgREST indépendant.

Trois modes de panne :
- échec au milieu → sections existantes modifiées, images remplacées, ordre
  partiel ; le rollback ne défait que les créations (`:187-207`) ;
- deux onglets → dernier save gagne, les sections absentes sont supprimées et
  leurs fichiers effacés (`:362-364`) ;
- retry après réponse perdue → les UUID temporaires ne sont pas reconnus →
  sections dupliquées (pas d'idempotence).

**Correctif** : RPC Postgres `save_webtoon(p_webtoon_id, p_sections jsonb)`
atomique ; colonne `revision` (ou vérification `updated_at`) pour le verrou
optimiste ; clé d'idempotence côté client (réutiliser l'UUID client comme id de
section et faire un upsert).

### DATA-3 — `syncImages` destructif

`actions.ts:417-444` supprime toutes les lignes `images` de la section puis
réinsère. Un échec d'insert (contrainte, réseau, id dupliqué) perd définitivement
les lignes. `upsertSection` appelle bien `syncImages` pour les sections existantes
(`:414`), donc le risque couvre tous les saves, pas seulement les créations.

**Correctif** : upsert des images entrantes puis suppression des ids absents, ou
RPC transactionnelle. À défaut, snapshot des lignes avant le delete pour restauration.

### DATA-4 — `deleteWebtoonAction` supprime le Storage avant la base

`actions.ts:528-550`. Si le delete DB échoue, le webtoon reste publié avec des
médias manquants, sans réparation possible.

**Correctif** : supprimer la ligne d'abord (cascade), puis nettoyer le Storage en
best-effort. Un orphelin Storage est récupérable ; un webtoon sans médias ne l'est pas.

### DATA-5 — Erreurs internes exposées + identifiants non validés

`errorMessage` (`actions.ts:85-87`) renvoie `error.message` brut (`db.saveWebtoon
failed: duplicate key ...`, `connection refused`). `webtoonId` est validé par
`z.string().min(1)` (`:25,38,43`) : `/read/foo` ou `/editor/foo` passent, puis
PostgREST envoie `eq("id","foo")` sur une colonne `uuid` → erreur `22P02` → 500.

**Correctif** : `z.uuid()` partout, message générique côté client, log structuré
côté serveur (sans secret), et `error.tsx` pour `/editor`.

### ED-1 — La sauvegarde écrase les éditions faites pendant l'`await`

`EditorDetailShell.tsx:104-111` : `sections` est la closure du clic. Pendant le
save (plusieurs secondes, cf. N+1), le canvas reste interactif. À la résolution :

```ts
setSections(remapSectionIds(sections, result.sectionIds)); // ancien tableau
setIsDirty(false);                                          // désarme le garde-fou
```

Toute section ajoutée/modifiée entre-temps est perdue. Aggravant : `revalidatePath`
(`actions.ts:366`) renvoie un payload RSC et `EditorCanvasClient.tsx:18-20`
refait `setSections(initialSections)`.

**Correctif** : compteur de révision dans le contexte ; à la résolution,
n'appliquer le remap qu'à l'état courant et ne remettre `isDirty` à false que si
aucune édition n'a eu lieu pendant le save. Ne réhydrater que sur changement de
`webtoonId`.

### ED-2 — Double soumission / retry = sections dupliquées

`performSave` (`EditorDetailShell.tsx:70-122`) n'a pas de verrou de ré-entrance
synchrone ; le bouton n'est désactivé qu'après le re-render. Un double-clic ou un
retry recrée les nouvelles sections (pas d'idempotence, cf. DATA-2).

**Correctif** : `useRef` de garde en entrée de `performSave` + idempotence serveur.

### ED-3 — Navigation interne sans garde

`EditorDetailShell.tsx:55-68` ne protège que `beforeunload`. Les liens « Retour à
l'éditeur » (`:186`) et « Lecteur » (`:201`) démontent l'éditeur sans confirmation.

**Correctif** : garde sur les `<Link>` (`confirm` si `isDirty`) + interception
`popstate`.

### ED-4 — Ré-upload d'une animation cassé par collision de chemins

`SectionConfigPanel.tsx:316-323` uploade les frames sur
`webtoons/sections/<id>/frames/<index>.webp` avec `upsert:false`
(`upload.ts:32`). Un deuxième upload complet sur la même section échoue dès la
frame 0 (« resource already exists »). Le sprite déjà uploadé reste orphelin.

**Correctif** : batch timestamp (`frames/<timestamp>/<index>.webp`) ou
`upsert:true` + suppression explicite des anciennes frames ; nettoyer le sprite
en cas d'échec.

### ED-5 — Chaque tick de slider crée une entrée d'historique

`SectionConfigPanel.tsx:987-993` : `onValueChange` du slider d'opacité appelle
`handleFxConfigChange` → commit → `past.push` (limite 50). Un seul glissement
vide l'undo précédent. Même problème sur les champs numériques (`:594-601`,
`:951-978`).

**Correctif** : état draft local + commit sur `onValueCommitted`/`onBlur`/`Enter`,
ou coalescing temporel (même section + champ < 500 ms → remplace le dernier snapshot).

### RD-1 — Inertie de molette/trackpad : saut de plusieurs étapes

`useReaderNavigation.ts:119-126,194-213` et `ReaderDeck.tsx:164-172`. Après une
navigation, l'accumulateur est remis à 0 mais aucun cooldown n'est posé.
`WHEEL_RESET_MS` (220 ms) ne s'applique qu'après une inactivité. L'inertie d'un
trackpad dure 0,5-1,5 s : les événements suivants re-remplissent le seuil
(~160 px) et repagent une étape. Au tactile, `handleWheel` est appelé à chaque
`touchmove` (`ReaderDeck.tsx:202`) : un swipe long traverse plusieurs sections.

**Correctif** : latch post-navigation (~200 ms) ou ignorer la molette jusqu'à
inversion du signe ; pour le tactile, accumuler et ne commiter qu'au `touchend`.

### RD-2 — `deltaMode` non normalisé : Firefox inutilisable

Aucun `deltaMode` dans `src` (vérifié). Firefox + souris émet
`DOM_DELTA_LINE` avec `deltaY = 3` ; il faut ~54 crans pour franchir le seuil de
160 px. `LongYStep.tsx:150,161` ne défile que de 3 px par cran.

**Correctif** : normaliser à la source :
`const delta = event.deltaY * (event.deltaMode === 1 ? 16 : event.deltaMode === 2 ? innerHeight : 1)`.
À faire **avant** de calibrer le cooldown de RD-1.

### IMG-1 — `fitWithin` ne borne que la largeur : les long-y échouent

`process.ts:200-209` : `MAX_CANVAS_DIMENSION = 16384` est comparé à `width`
seulement. Une planche `1200×30000` passe telle quelle → `canvas.toBlob` renvoie
`null` (`ENCODE_FAILED`) ou l'onglet meurt (Safari ~16,7 M px, Chrome ~600 Mo).
Le test `process.test.ts:205-211` verrouille même `16384×9000`.

**Attention** : un simple clamp de la hauteur à 16384 est **dangereux** pour
`long-y`, qui rend une image unique (`LongYStep.tsx`). Downscaler la moitié d'un
strip casse le format. La bonne réponse est la **segmentation à l'upload** (tuiles
de hauteur bornée, rendues à la suite), ou un plafond par type avec avertissement
UX explicite. À sortir des « quick wins ».

### IMG-2 — `resizeImage` ne réduit jamais ; `maxDimension` est mort

`ProcessOptions.maxDimension` (`process.ts:97`) n'est lu que par
`buildSpriteSheet` (`:279,322`). `resizeImage` (`:223-242`) ne l'applique pas :
une photo `4000×6000` est convertie en WebP q=0.9 sans downscale. Le test
`process.test.ts:178-190` verrouille ce comportement.

**Correctif** : appliquer `maxDimension` (1600 px sections, 800 px covers) et une
qualité ~0.8 ; mettre à jour le test. Prévoir un backfill des assets existants.

### IMG-3 — `buildSpriteSheet` décode toutes les frames en parallèle

`process.ts:289-303` fait `Promise.all(files.map(decodeImage))`, puis calcule le
`scale` mémoire `:310-320`. 100 frames 1600² ≈ 1 Go décodé avant l'application de
`MAX_SPRITE_PIXELS`. Le commentaire affirme l'inverse.

**Correctif** : décodage séquentiel ou concurrence 4, `createImageBitmap(blob, {
resizeWidth })` dès le décodage, rejet `files.length > 120`.

### INF-1 — Secrets de production dans le contexte Docker

`.dockerignore:10-12` n'exclut que `.env` et `.env.local`. `.env.dokploy` et
`.env.dockertest` contiennent une service role réelle (vérifié sans afficher les
valeurs), sont bien git-ignored, mais entrent dans `COPY . .`
(`Dockerfile:22-24`) et donc dans les couches/cache BuildKit du build stage.

**Correctif** : `.env*` + `!.env.example` dans `.dockerignore` ; supprimer ces
fichiers du disque de build ; **faire tourner les clés** si une image a déjà été
construite et poussée avec eux.

### INF-2 — E2E non exécutables, zéro CI, pas de `typecheck`

- `tests/e2e/e2e-flow.test.ts:34` et `editor-fx-flow.test.ts:21` lisent
  `SUPABASE_SERVICE_ROLE_KEY` sans charger `.env.local` (seul
  `product-flow.test.ts` a `loadLocalEnv`) → 401 sur 2 fichiers sur 3.
- `.github/workflows/` absent : aucun lint/test/build/typecheck sur PR.
- `package.json` n'a pas de script `typecheck`.

**Correctif** : chargeur d'env partagé pour les E2E, workflow
`npm ci → lint → tsc --noEmit → vitest → build`, script `typecheck`. C'est le
prérequis qui rend les autres vagues vérifiables.
